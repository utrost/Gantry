## Next slice: installed workflows and upgrades

The follow-up to initial packaging adds installed-runtime acceptance and a real
native upgrade scenario on both CI platforms. The synthetic older installer uses
the current code with an older version identity, so it validates packaging and
state preservation rather than historical application-schema compatibility.

The clean Java 17 build passed 465 tests with zero failures/errors/skips. Local
extracted baseline/candidate launchers passed all eight workflow checks, preserved
the four persisted file hashes, and launched the candidate GUI without system
Java. Focused tests passed for complete seed/verify workflows, existing-profile
protection and detection of corrupted persisted settings. Four Python packaging
tests cover version ordering, invalid versions, fixture isolation and rejecting
equal/newer baselines. Updated full-build and cross-platform results are recorded
in the PR checks and attached `validation-<runner>` artifacts.

The automated checks now cover:

- SVG import and PNG centerline vectorization/import;
- editable project, settings, history and recovery loading;
- mock plot completion and cancellation with pen raised;
- G-code file export;
- native older-to-candidate replacement and installed version identity;
- profile hashes unchanged across upgrade, launch-directory changes and uninstall;
- menu shortcut presence after upgrade and removal on uninstall;
- upgraded GUI launch using bundled Java.

The remaining checkboxes above still describe **human desktop/hardware**
acceptance. Service-level acceptance and shortcut-file checks do not prove the
complete guided mouse/keyboard workflow or physical controller behavior.

Upgrade run `36230236702` passed on Windows Server 2022, including all eight
installed workflow checks, OS profile resolution, product replacement, shortcut
presence, GUI launch and uninstall preservation. Its Linux job installed and
upgraded correctly but exposed an overly narrow shortcut assertion in the test:
XDG can register the launcher in `/usr/local/share/applications` as well as
`/usr/share/applications`. The check now searches both defaults and configured
XDG roots and verifies the desktop entry's launch target. A regression test covers
that discovery behavior. Verification now launches from the installation directory
(root-owned on Linux) and rejects any configuration/history/recovery files leaked
there. Final rerun reports are linked in PR #28.
